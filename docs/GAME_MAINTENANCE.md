# Editing the games

The eight formerly inline games use classic JavaScript files. No build step or new framework is required. `animal-rescue-train` and `flash-brain` retain their existing module/build structures.

| Change | File |
| --- | --- |
| Game-specific layout, colors, responsive styles | `games/<id>/style.css` |
| Question generation, difficulty, scoring calculations | `games/<id>/rules.js` |
| Canvas graphics and visual effects | `games/<id>/renderer.js` |
| Sound synthesis and audio controls | `games/<id>/audio.js` |
| Start/pause/retry, input, live state, records and SDK integration | `games/<id>/main.js` |
| HTML containers and script/style load order | `games/<id>/index.html` |
| Spot Quick specimens / Shadow Match silhouettes | Their `shapes.js` |
| Space Scale archetypes / Tap Match shapes and colors | Their `data.js` |
| Shared title/result content | `shared/toenow-screen-config.js` and language catalogs |
| Shared title/result rendering and styles | `shared/toenow-screens.js`, `assets/unified-title-menu.css` |

## Module boundaries

`rules.js`, `audio.js`, `shapes.js` and `data.js` expose their APIs under `window.ToenowGameModules[gameId][part]`. They also support `require()` for Node tests. Each game keeps its own rules; a similar-looking timer or score formula is not automatically a shared rule.

`renderer.js` exposes `createRenderer(scene)`. `main.js` supplies explicit getters for its current state, dimensions, board and buffers. Keep these getters: copying a mutable primitive or a replaceable board into the renderer would leave it stale after resize/restart. The renderer owns drawing, not score persistence, input binding or the game loop.

The controller mounts `ToenowScreens` before querying the buttons generated by it. Keep the existing shared SDK order, then load game data/shapes before dependent rules, audio and renderer before `main.js`. Keep these scripts synchronous and in order unless initialization and tests are deliberately updated together.

Stylesheets remain beside the original HTML, so relative asset URLs keep the same base. Storage keys, practice guards and screen ownership were preserved during extraction. Do not duplicate title/result templates or migrate saved records as part of routine UI work.

## Verification

During iteration, run the relevant focused check:

```powershell
npm run test:modules
node --test tests/games-runtime.test.cjs tests/practice-mode.test.cjs
```

For a single game's real shared-screen flow, use the configured Playwright runtime and your local server URL:

```powershell
$env:TOENOW_TEST_URL = 'http://127.0.0.1:8765'
$env:TOENOW_TEST_GAMES = 'spot-quick'
node tools/verify-shared-screens-browser.cjs
```

At completion, run `npm test`. For changes affecting all games/shared screens, remove the filter and run the complete browser regression required by AGENTS.md:

```powershell
Remove-Item Env:TOENOW_TEST_GAMES -ErrorAction SilentlyContinue
node tools/verify-shared-screens-browser.cjs
```

Source-inspection tests/tools use `tools/lib/game-source.cjs` to read local scripts/styles in document order. Do not assume gameplay code is inline in HTML. The shared-screen browser suite instruments `main.js` directly so it still verifies real external resource loading. Browser checks on desktop Edge do not verify physical iPad Safari.
